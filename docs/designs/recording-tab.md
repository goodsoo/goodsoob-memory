## Problem Statement

맥북 메뉴바 녹음기와 아이폰 음성 메모 녹음은 이미 `~/brain/_audio/` 로 자동 수집되고, Pro 에서 30분마다 whisper 1차 전사까지 자동으로 끝난다(`~/.claude/skills/transcribe/scripts/auto_stt.sh`, 산출물 `_audio/.stt/<base>/tr.json·tr.txt·done`). 그런데 그 다음 단계(화자분리 → 교정 → 정리)는 터미널에서 `/transcribe` 를 직접 돌려야만 진행되고, 짱수메모리는 이 녹음들의 존재 자체를 모른다. 결과: 2026-10-28 기준 whisper 만 돌고 교정 안 된 녹음이 `.stt/` 에 22개 쌓여 있다.

목표: 짱수메모리 안에서 녹음을 보고, 인원 수를 정하고, 교정 리뷰를 하고, 결과를 알맞은 곳(기존 메모 / 새 메모 / 보관만)으로 보내는 흐름을 터미널 없이 끝낸다.

## What Makes This Cool

- 녹음이 "처리할 일" 로 앱에 떠오른다. 오늘 대시보드에 "처리할 녹음 N개", 클릭 한 번이면 녹음 탭.
- 행선지를 **전사가 끝난 뒤, 내용을 보고** 고른다. 회의 중 적던 메모가 있으면 거기 붙이고, 없으면 그 녹음에서 새 메모를 만든다.
- 전사본은 언제나 한 벌. 연결 전엔 `_audio`(git·색인 제외), 연결하면 메모 옆 사이드카로 이사해 메모를 따라다닌다. 연결된 전사본은 기존 사이드카처럼 brain git(원격 없음)에 들어가고, gbrain 색인 여부는 PR1 전에 확인한다(Open Questions 8).
- 폰 PWA(tailscale)에서도 리뷰 딸깍을 할 수 있다. 무거운 계산은 Pro 서버가 한다.

## Constraints

- **프라이버시 (transcribe `SKILL.md:56`)**: 교정·제목·요약(Claude 로 내용이 가는 단계)은 자동 실행 금지, 명시 실행만. 앱 버튼 클릭을 명시 실행으로 보되, 외부 전송 단계는 별도 버튼으로 분리하고 전송 사실을 버튼 옆에 표시한다. auto_stt 의 자동 범위(수집 + whisper)는 그대로.
- **화자분리 자동 금지**: 화자 수를 모르면 과분할(76분 → 115명 실측). 인원 수는 사용자가 입력.
- **Pro 전용 계산**: whisper·sherpa-onnx·모델은 Pro 에만 있다. `~/.auto-stt-enabled` 마커가 있는 맥만 job 실행. 에어 fallback 서버(`deploy/air-fallback.sh`)에서는 job 버튼 비활성 + 이유 표시.
- **전사본 자리 = 연결 전 `_audio`, 연결 후 메모 옆** (2026-10-29 eng review 결정): 녹음 파일은 언젠가 지워도 되는 부산물이고 남는 것은 메모에 붙은 전사본이다. 그래서 연결 전(미정·보관됨)에는 `_audio/<base>.txt`(git·색인 제외, `~/brain/RESOLVER.md:39`), 연결하면 메모 옆 사이드카 `<메모>.transcript.md` 로 **이사**한다. 사이드카는 메모 rename 을 따라간다(`src/api/meetings.ts:206-214` `renameMeetingFiles`). 사이드카는 brain 본문이라 brain git 에 추적된다 — 기존 18개도 전부 추적 중(`git ls-files`, 2026-10-29)이고 brain git 은 원격 없음. 스킬 규칙 "전사본 = 원자료, `_audio`"(`SKILL.md:27`)과는 연결된 녹음에 한해 달라진다 → 스킬 문서에 한 줄 명시.
- **이중 writer 위험**: brain 은 iCloud + gbrain-sync 데몬이 스캔한다(learning `ios-pwa-eviction-and-brain-icloud-git`). job 중간물은 `_audio/.stt/<base>/` 안에만.
- **오디오 seek = HTTP Range 필수** (`SKILL.md:133`). 현재 `/api/attachment` 는 `Uint8Array` 로 응답해 Range 가 안 된다(`server/index.ts:469`). Bun 1.4.3 의 `new Response(Bun.file(abs))` 는 Range 요청에 206 + `content-range` 를 자동으로 돌려준다(2026-10-29 실측: `bytes 100-199/7612`). `/api/audio` 는 `Bun.file` 로 응답하고 206 을 직접 구현하지 않는다.
- **코덱**: 브라우저 `<audio>` 는 ALAC 재생 불가(`SKILL.md:134`). 2026-10-28 실측 4개(음성 메모 원본 `20260722-1402` 포함) 모두 `aac`. 그래도 `ffprobe` 코덱 체크를 두고 aac 가 아니면 `.stt/<base>/play.m4a` 로 AAC 변환본을 만들어 그걸 서빙(Pro 전용, 첫 재생 요청 시 1회).
- vault schema 룰(CLAUDE.md): `audio:` 는 신규 필드(default 빈 배열) → migration 불필요. 기존 사이드카 18개는 그 자리 그대로 둔다(이전 없음).
- DS: goodsoob-design-system consumer. 리뷰 UI 는 DS 컴포넌트로.

## Premises (확정)

1. 연결은 **자동 확정하지 않는다.** 리뷰 후(또는 초벌 전사 상태에서 바로) **행선지 3택** 중 사용자가 고른다: 기존 메모에 연결 / 새 메모로 만들기 / 전사만 보관. 기존 메모 후보는 정렬만 해준다. 근거: 노트 1,975개 중 `date:` 518 · `time:` 82 · `attendees:` 44 개라 자동 매칭 근거가 약하고, 오연결은 남의 회의가 섞이는 신뢰 파손이다.
2. 연결 정보는 **메모 frontmatter `audio:`** 에 base 배열로(`audio: [20261028-1300]`). `updateMeeting`(`src/api/meetings.ts:196`)은 패치한 키만 frontmatter 에 반영하고 `id:` 를 주입하지 않는다 → id 없는 brain 노트에도 `audio:` 키 하나만 추가(date/time 편집과 같은 수준의 변경). 링크 방향이 노트→녹음이라 노트 rename(합성 uid 변경)에도 링크 유지. 연결 후 `audio:` 는 **▶ 재생·녹음 탭 이동용 참조**일 뿐 전사본은 사이드카에 있으므로, 녹음 파일이 rename·삭제돼도 전사본은 그대로고 ▶ 만 사라진다.
3. 파이프라인 로직의 단일 소스 = transcribe 스킬 `scripts/`. 앱 서버는 `diarize.py`·`merge.py`·`normalize.py`·`anchor_offsets.py`·`apply_decisions.py` 를 호출만 한다.
4. 무거운 작업(화자분리, Claude 교정 후보)은 **서버 job**, Pro 에서만. 탭·폰을 닫아도 계속, 상태는 `.stt/<base>/job.json`.
5. **전사본은 언제나 한 벌.** 연결 전엔 `_audio/<base>.txt`, 연결하면 메모 사이드카로 **이사**(복사 아님 — 이사 후 `_audio/<base>.txt` 삭제). 음성 기록 탭·요약 입력(`buildClaudePrompt`)은 지금처럼 사이드카 하나만 읽는다. 기존 `.transcript.md` 사이드카(18개, 전부 `angel-robotics/notes/Meetings/`)는 손대지 않는다.
6. 스킬 §9 의 보장(큐레이션 요약 · 원자료 링크 · 품질 게이트)은 **앱 v1 흐름에서 제공하지 않는다.** "새 메모" 는 빈 본문 + `audio:` 링크(= 원자료 링크) 로 시작하고, 요약은 사용자가 요약 탭에서 `SummaryModal` 로 실행한다. 품질 게이트가 필요한 녹음은 터미널 `/transcribe` 를 계속 쓴다. 스킬 문서에 이 차이를 한 줄 명시.
7. 앱 흐름에서는 녹음 파일명을 바꾸지 않는다. 바깥에서 바뀌어도 연결된 메모의 전사본은 안전하고, 깨지는 것은 ▶ 재생과 녹음 탭 이동뿐이다("녹음 파일 없음" 표시).
8. 진입점은 **녹음 중심**: 녹음 탭(2군)에서 메모를 고른다.

## Approaches Considered

- **A: 인박스 + 연결만** (화자분리·교정은 터미널 유지) — 기각: "인원 수 지정·리뷰도 앱에서" 요구 미충족. B 의 PR1 으로 흡수.
- **B: 녹음 탭 + 앱 안 파이프라인 + React 리뷰** — 채택.
- **C: B + `build_review.py` HTML iframe 리뷰** — 기각: DS·테마·단축키 밖, 폰 사용성 불확실, 스킬에 POST 훅 수정 필요. 실제 계약은 `anchored.json` 이라 React 재구현 비용이 작다.
- **탭 없이 오늘 블록 + 모달** — 기각: 상태 여러 단계의 작업 흐름. 루틴의 "오늘 블록 + 2군 탭" 선례(`SIMPLIFY.md:73`, `src/components/nav/tabs.ts:15`)를 따른다.
- **전사본 복사(사이드카 + `_audio` 양쪽)** — 기각: 교정본이 두 벌.
- **전사본 `_audio` 단일(메모는 참조만) + 기존 사이드카 18개 이전** — 기각(2026-10-29 eng review): 녹음 파일명이 바뀌면 메모의 전사본 연결까지 끊기고, 사이드카를 다루는 9개 파일 수정 + 이전 작업이 필요하다. 녹음은 부산물이라 전사본은 메모를 따라가는 편이 맞다.

## Recommended Approach

### 화면 구성

- **녹음 탭** (`#recordings`, `tabs.ts` 의 할 일 뒤 2군 자리)
  - 사이드바: 녹음 목록, 상태별 그룹 + 날짜 desc. 행 = 녹음 시각 · 길이 · 상태 칩 · 연결된 메모 제목.
  - 메인: 오디오 플레이어 · 전사 미리보기 · 상태별 주 액션 · 행선지 패널(행선지가 연결됨·보관됨이면 "연결 해제 / 다른 메모로 이동 / 보관 취소").
- **오늘 대시보드**: "처리할 녹음 N개" 한 줄. N 정의는 아래 "녹음 상태" 참조. 0이면 숨김.
- **메모장**: `audio:` 가 있는 메모는 음성 기록 탭 옆 녹음 배지 → `#recording-{base}`.

### base 이름 파싱

- `YYYYMMDD-HHmm` (메뉴바 녹음기·음성 메모 import), `YYYYMMDD-HHmmss`, `-vm` 충돌 접미사, `YYYYMMDD-HHmm_주제_사람`·`YYYYMMDD_주제_사람`(옛 `/transcribe` 결과) 을 정규식으로 date/time/label 분리. 어느 패턴에도 안 맞는 이름(음성 메모 import 의 `New-Recording-3` 류, `auto_stt.sh:36`)은 label = 이름 전체, 시각은 아래 fallback. `audio:` 값은 읽을 때 `String()` 으로 정규화(숫자만인 base 가 YAML 숫자로 읽혀 문자열 일치가 깨지는 것 방지).
- 날짜만 있으면 시각 미표시, 아무것도 안 맞으면 `ffprobe creation_time` → 그래도 없으면 날짜 미상 그룹.
- `.stt/*` 스캔은 **디렉터리만**(`imported-voicememos.txt` 등 파일 제외).

### 녹음 상태 — 두 축 (서로 독립)

**행선지 축** (어디로 갔나):

| 값 | 판정 |
|---|---|
| 연결됨 | 어떤 메모의 `audio:` 에 base 가 있음 |
| 이사 미완료 | 연결됨인데 `_audio/<base>.txt` 가 남아 있거나 `moved.json` 이 없음(link 도중 중단) → 녹음 탭 진입 시 서버가 link 를 다시 실행해 마무리(멱등) |
| 휴지통 | 휴지통 메모의 `audio:` 에만 base 가 있음 (주 액션: 메모 복원 = 기존 휴지통 복원, 메모·사이드카가 함께 돌아와 연결됨 복귀) |
| 보관됨 | `.stt/<base>/archived` 존재 (연결됨이 우선) |
| 미정 | 그 외. 단 `moved.json` 이 있는데 어느 메모(휴지통 포함)에도 base 가 없으면, 서버가 brain 전체 `*.transcript.md` 에서 ` · <base>` 헤딩을 한 번 찾아본다(메모가 `_` 폴더로 옮겨졌거나 앱 밖에서 rename 된 경우 대비). 찾으면 그 메모를 "연결 정보 없는 섹션"으로 보여주고 `audio:` 복구 버튼, 못 찾으면 = 휴지통을 비워 전사본이 사라진 것 → **전사본 없음** 표시 + "초벌 전사로 다시 만들기"(`.stt/<base>/tr.txt` → `_audio/<base>.txt`, `moved.json` 삭제, `raw-promoted` 마커) |

**파이프라인 축** (전사가 어디까지 왔나) — 위에서부터 첫 번째 일치:

| # | 값 | 판정 | 주 액션 |
|---|---|---|---|
| 0 | 텍스트만 | `<base>.m4a` 없음 (옛 `/transcribe` 결과 등 `<base>.txt` 만) | (없음, 플레이어·job 숨김) |
| 1 | 처리 중 | `job.json.state == running` + pid 생존 | (없음, 진행 표시) |
| 2 | 오류 | `job.json.state == error` (pid 사망 감지 포함) | 재실행 / 실패 청크만 재실행 |
| 3 | 리뷰 대기 | `anchored.json` 존재 | 리뷰 |
| 4 | 교정 대기 | `화자분리.txt` 존재 (화자분리 완료, Claude 교정 미실행) | 교정 후보 만들기 (Claude 전송) |
| 5 | 교정본 | (`<base>.txt` 존재 또는 `moved.json`) + `raw-promoted` 없음 | (없음) |
| 6 | 초벌 전사 | `.stt/<base>/done` 존재 (또는 `<base>.txt`·`moved.json` + `raw-promoted`) | 화자분리 (인원 수 입력) |
| 7 | 전사 대기 | 그 외 (m4a 는 있고 위 조건 모두 불일치) | (없음, auto_stt 대기) |

0번을 맨 먼저 평가하므로 1~7은 모두 m4a 가 있는 녹음에만 적용된다.

- **휴지통 정책(2026-10-29 eng review)**: 메모를 휴지통에 버리면 전사본도 사이드카와 함께 휴지통으로 간다(`src/api/meetings.ts:142-150` 기존 동작, 휴지통 코드 무변경). 녹음 스캔은 휴지통 메모의 `audio:` 도 읽는다.
- **사이드바 그룹 = 행선지 축**(미정 / 연결됨 / 휴지통 / 보관됨), 행의 상태 칩 = 파이프라인 축. 텍스트만 항목은 사이드바 기본 필터에서 숨김("텍스트만 보기" 토글).
- 메인 화면 주 액션 = 파이프라인 축이 주고, 행선지 미정이면 행선지 패널을 같이 띄운다.
- 처리 중 판정은 행선지와 무관하므로 연결된 녹음의 job 도 `refetchInterval` 트리거가 걸린다.
- **API 전제조건**: diarize 는 `.stt/<base>/done` 필요(없으면 409 — `auto_stt.sh:56-60` 은 whisper 성공 후에만 `done` 을 만든다, `tr.json` 단독은 실패 잔재일 수 있음), corrections 는 `화자분리.txt` 필요(없으면 409), apply 는 `anchored.json` 필요(없으면 409). 처리 중이면 셋 다 409.
- 오늘 블록 N = **행선지 미정이면서 파이프라인이 텍스트만·전사 대기·처리 중이 아닌 녹음** + **행선지와 무관하게 파이프라인이 오류·리뷰 대기·교정 대기인 녹음**(중복 제거).

### 행선지

- **초벌 전사에서 바로 행선지**를 고르면, whisper 원본 `tr.txt` 를 전사본으로 쓴다(보관이면 `_audio/<base>.txt` 로 복사, 연결이면 바로 사이드카로). 교정 전 원본임은 `.stt/<base>/raw-promoted` 마커로 표시.
- **이사(연결 시)**: ① 사이드카 끝에 `## {녹음 시각} · {base}` 헤딩 + 전사본 추가 → ② 메모 `audio:` 에 base 추가 → ③ `.stt/<base>/moved.json` = `{hash, raw}`(이사한 텍스트의 해시, raw-promoted 여부) + `.stt/<base>/done` 보장 → ④ `_audio/<base>.txt` 삭제. 중간 실패 시 다음 시도에서 사이드카에 같은 base 헤딩이 이미 있으면 ①을 건너뛴다(멱등). ③의 `done` 은 필수 — auto_stt 는 `<base>.txt` 또는 `.stt/<base>/done` 이 있으면 건너뛰므로(`auto_stt.sh:47-48`), `.txt` 를 지운 뒤 재전사되지 않게 한다. ①~④는 서버 `POST /api/recordings/:base/link` 한 곳에서 **메모 경로 기준 mutex** 안에서 실행하고(같은 메모에 두 녹음을 동시에 연결해도 섹션이 사라지지 않게), 클라이언트는 이 호출을 `scope: meeting:${uid}` mutation 으로 걸어 같은 탭의 그 메모 저장과 직렬화.
- **기존 메모에 연결**: 후보 정렬 = ① 메모 `date` 가 녹음 날짜와 같고 mtime 이 녹음 구간 안 ② 같은 날짜 ③ QuickSwitcher 검색. ①은 이후 편집·iCloud sync 로 mtime 이 밀리면 약해지는 휴리스틱일 뿐이다. 확정 = `audio:` 배열에 base 추가.
- **새 메모로 만들기**: 제목·폴더 입력(기본 `inbox`, `createMeeting` 기본값). 본문 빈 상태 + `audio: [base]` + date/time = 녹음 시각. 메모 생성과 이사는 `POST /api/recordings/:base/link {newMemo: {title, folder}}` 한 요청 안에서 같은 mutex 로 처리(클라이언트가 create → link 를 따로 부르지 않는다). 생성 후 그 메모로 이동.
- **전사만 보관**: `.stt/<base>/archived` 마커.
- **되돌리기**: "연결 해제" = 사이드카에서 그 base 헤딩 섹션을 잘라 `_audio/<base>.txt` 로 되돌림 → `audio:` 에서 base 제거 → `moved.json` 삭제. 섹션 헤딩을 찾지 못하면(사용자가 헤딩을 지웠거나 고침) 텍스트는 건드리지 않고 `audio:` 만 제거 + "전사본은 메모에 남아 있습니다" 안내(데이터 손실 방지). "다른 메모로 이동" = 해제 + 연결. "보관 취소" = `archived` 삭제.

### 메모 쪽 음성 기록 탭

- 지금 구조 그대로: 음성 기록 탭 = 사이드카 하나(`DocSnapshot.transcript: string`, `MeetingForm.tsx:84-86`). 편집·undo·저장·업로드(`MeetingForm.tsx:1742`)·휴지통·export 경로는 바꾸지 않는다.
- **1메모 = n녹음 규칙**:
  - **구분**: 녹음마다 `## {녹음 시각} · {base}` 헤딩 섹션. 헤딩 판정 = `## ` 로 시작하고 ` · <base>` 로 끝나는 줄, 단 `<base>` 는 그 메모 `audio:` 의 값과 **문자열 그대로 일치**할 때만(정규식 문자 클래스로 base 를 뽑지 않는다 — base 에 공백·`-`·한글이 들어갈 수 있다, 예 `20260826_카페미팅_정진용-공경철`). 기존 사이드카 내용(헤딩 없음)은 맨 앞 머리말로 그대로 둔다.
  - **순서**: 이사할 때 녹음 시각 기준으로 알맞은 자리에 끼워 넣는다(시각 미상은 맨 뒤). 그 뒤 사용자가 순서를 바꿔도 앱은 다시 정렬하지 않는다.
  - **섹션 플레이어**: `TranscriptView`(보기)가 위 헤딩 옆에 ▶ 버튼을 그린다. 누르면 그 섹션 위에 작은 `<audio>`(`/api/audio?base=`)가 열리고, 한 번에 하나만 재생. m4a 가 없으면(삭제·rename·텍스트만) ▶ 대신 "녹음 파일 없음". 헤딩의 base 는 녹음 탭 링크(`#recording-{base}`).
  - **요약 입력**: 사이드카 전체 그대로(변경 없음).
  - **부분 연결 해제**: 위 "되돌리기" — 그 섹션만 빠지고 나머지 유지.
- **열린 폼과의 충돌 — 확인됨, PR1 선행 수정 (D5, 2026-10-29)**: 메모 폼은 본문만 고쳐도 `docToPatch`(`MeetingForm.tsx:117-124`)가 transcript 를 매번 같이 보내고, 빈 값이면 사이드카를 삭제한다(`src/api/meetings.ts:243-247`). 폼 상태는 uid 별 `HISTORY_CACHE` 에 세션 내내 남아 디스크 변경을 다시 읽지 않는다(`src/hooks/useStateHistory.ts:120-156`). 그래서 메모를 연 뒤 녹음 탭에서 연결하고 돌아와 본문을 한 글자 치면 이사한 섹션이 지워진다(같은 탭에서도 발생, 연결 해제·apply·Cmd+Z 도 동일). 수정:
  - `docToPatch` 는 마지막 commit 이후 **바뀐 칸만** 보낸다(본문·transcript·summary·meta 각각).
  - link·unlink·apply 성공 후 해당 uid 의 history cache 를 버리고 디스크 내용으로 다시 시작(`useStateHistory` 에 `reset(value)` 추가). Cmd+Z 는 그 경계 너머로 가지 않는다.
  - 회귀 테스트(CRITICAL): 메모 열기 → link → 본문 수정 저장 → 사이드카 섹션 유지 / 기존 transcript 가 있던 메모도 동일.
  - 부수 효과: 앱 밖(Claude Code 등)에서 고친 사이드카를 본문 저장이 덮어쓰던 기존 문제도 함께 줄어든다(transcript 를 안 건드리면 안 보냄).

### 서버 (server/index.ts 에 추가)

- `GET /api/recordings` — `_audio/*.m4a` 와 `_audio/*.txt` base 합집합 + `.stt/*` 디렉터리 → 상태 계산용 원자료 반환. 연결된 녹음의 m4a 를 지우면 목록에서 빠진다(전사본은 메모에 있으므로 손실 없음, `.stt/<base>/` 잔재는 목록 대상 아님). 길이는 `.stt/<base>/meta.json` 에 ffprobe 결과 캐시(없을 때만 실행). iCloud dataless(다운로드 안 된) 파일은 ffprobe 생략 + "동기화 대기" 표시.
- `GET /api/audio?base=` — m4a(또는 `play.m4a`) 를 `new Response(Bun.file(abs), {headers: {"Content-Type": "audio/mp4"}})` (Range 는 Bun 이 처리). base 는 `^[^/\\]+$` + 기존 세그먼트 traversal 가드.
- `POST /api/recordings/:base/link` `{memo}` / `POST /api/recordings/:base/unlink` — 위 이사·되돌리기 순서를 서버 한 곳에서 실행. link·unlink·apply 는 **메모 경로 기준 mutex**(대상 메모의 사이드카 read-modify-write 를 직렬화), job 은 base 기준 mutex.
- `POST /api/recordings/:base/diarize` `{speakers, names}` — 로컬 전용 단계(1~3). `POST /api/recordings/:base/corrections` — Claude 전송 단계(4~5). 버튼을 둘로 나누고, 두 번째 버튼 옆에 "전사 내용이 Claude 로 전송됩니다" 표시.
- Pro 가드: 마커 없으면 409 + 이유.
- **성능 메모(eng review)**: `_audio` 는 현재 파일 45개 안팎이라 스캔·상태 계산은 요청당 `readdir` 2회 + `.stt/<base>/` 마커 stat 수준(녹음 수 N 에 선형, N≈수십). ffprobe 는 `meta.json` 캐시로 녹음당 1회. 역참조(녹음 → 메모)는 이미 로드된 메모 목록(`useMeetings`, 노트 약 1,975개)의 `audio:` 에서 클라이언트가 계산 — 서버가 메모를 다시 스캔하지 않는다. 휴지통 메모 `audio:` 는 휴지통 목록 로드분 재사용. iCloud dataless m4a 를 `/api/audio` 가 바로 열면 다운로드 완료까지 응답이 멈출 수 있으므로, dataless 면 `brctl download` 를 걸고 503 + "동기화 대기" 를 돌려준다(재생 버튼에 표시).

### job lifecycle

- `job.json` = `{state: running|done|error, step, pid, startedAt, heartbeatAt, error}`.
- 같은 base 에 `running` + pid 생존이면 새 요청 409(데스크탑·폰 동시 클릭 방지).
- **락 규칙(단순화, eng review)**: 서버는 단일 Bun 프로세스이고 job 은 Pro 에서만 돈다. in-process per-base mutex 안에서 "`job.json` 확인 → spawn → `job.json {state: running, pid, startedAt}` 기록" 을 원자적으로 수행(동시 요청은 409). 서버 재시작 후에는 `job.json` 의 pid 가 살아 있고 `ps -o lstart= -p <pid>` 시작 시각이 `startedAt` 과 맞을 때만 실행 중으로 본다. `job.lock` 디렉터리·`owner.json`·lockId·60초 grace 는 두지 않는다.
- runner 는 `bun server/jobRunner.ts <base> <kind>` 를 `Bun.spawn(..., {detached: true})` + `unref()` 로 실행. detached 자식은 자기 process group 을 갖고 ppid=1 로 붙는다(2026-10-29 실측) — launchd 가 서버를 재시작해도 runner 는 살아남으므로 plist 는 바꾸지 않는다.
- 상태 read 마다 `process.kill(pid, 0)` 로 생존 확인. 죽었는데 running 이면 `error: interrupted` 로 갱신. runner 는 30초마다 heartbeat.
- 단계와 산출물 (전부 `.stt/<base>/`):
  1. WAV 변환 → `/tmp/<base>.wav` (끝나면 삭제)
  2. `diarize.py` → `diar.tsv` → `merge.py` → `화자분리.txt`
  3. `normalize.py` (in-place) → `normalize.log`
  4. Claude 교정 후보 → `corrections.json`
  5. `anchor_offsets.py` → `anchored.json`
- **보존**: apply 성공 후 `diar.tsv`·`corrections.json`·`anchored.json`·`normalize.log`·`화자분리.txt` 삭제(스킬과 같은 "중간물 버림"). `done`·`meta.json`·`raw-promoted`·`archived` 마커와 `tr.json`(seek 용) 은 유지.

### R3-2 — feasibility (blocking)

**Problem**

> The stale-lock rule races in exactly the desktop-plus-phone double-click case the lock exists to prevent. Request A runs mkdir job.lock, then spawns the runner, then writes the new pid to job.json. If request B arrives between A's mkdir and A's job.json write, B finds job.json missing or still holding the previous finished or errored run's dead pid. B treats the live lock as stale, deletes it, re-acquires it, and spawns a second runner. Both runners then write the same .stt/<base>/ artifacts. PID reuse after a dead runner can also make a stale lock look live.

**Remedy**

> Make check-and-spawn atomic. Either use an in-process per-base mutex in the single Bun server around 'mkdir → spawn → write job.json', or write an owner record (server token, acquiredAt) inside job.lock before spawning and treat a lock as stale only when job.json's startedAt or pid belongs to this lock and that pid is dead, or after a grace period. Record a start timestamp alongside the pid to guard against pid reuse.
