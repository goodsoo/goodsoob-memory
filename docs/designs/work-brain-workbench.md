## Problem Statement

goodsoob 앱이 4개(+blog, design-system)로 늘면서 경계가 흐려졌다. 특히 tower를 만든 뒤 work의 역할이 흐릿해졌다. 두 겹침 구역:

- work ↔ tower: 둘 다 "일·프로젝트·할일"을 만짐
- work ↔ growth: 둘 다 "글쓰기·루틴"을 만짐

work를 tower에 흡수할지, 역할을 확실히 나눌지 결정이 필요.

## What Makes This Cool

work가 "업무관리 앱의 잔재"에서 **"내 세컨드 브레인의 사람쪽 편집 표면"**으로 뒤집힌다. 브레인의 원본은 결국 md 파일 뭉치(회의록·음성 STT·내가 쓴 글·문서)다. 기계(gbrain)는 그걸 인입·임베딩·검색하고, 사람은 work로 읽고 쓴다. 같은 파일, 두 얼굴. work가 왜 존재하는지가 완벽히 선명해진다: **지식 베이스의 원자재를 다루는 작업대.** 별도 vault도, 앱 간 sync도 사라진다(남는 파이프라인은 gbrain 색인 하나뿐).

## Constraints

- 1인 본인 사용, 빌더 모드. Over-engineering 회피가 북극성.
- work = Tauri 데스크탑 + 정교한 md 에디터(3탭·라인 거터·transcript 화자색·undo 스택·AI 요약 모달). 이 에디터 자산은 유지.
- tower = 바닐라 Node + 바닐라 JS/CSS, 의존성 0, 노빌드가 북극성. 이미 할일을 md(`plans/<프로젝트>.md`)로 저장.
- growth = 바닐라 Node, 습관을 md frontmatter로. 이미 일기/시집/수필 창작 글쓰기 보유.
- **브레인 통합 (2026-09-15 결정):** 개인 brain `brain-work`(업무+인프라+범용)와 `brain-personal`(창작·개인사·일기·상담)을 **한 brain `~/brain/`으로 합친다.** 옛 분리 근거(RESOLVER §0 "회사 맥 노출" 머신축)는 은퇴 — 업무 brain도 회사 공유 안 하는 내 것 + Pro 맥도 나 혼자 씀 → 노출축 무의미, 통합이 관리·AI검색 둘 다 편함. work의 1차 대상 = 이 통합 brain. **회사 `angel_brain`(AIFT 회사 지식, research 맥)은 별개 축이라 hard wall 유지.** (근거·상세 = 지속메모리 `brain-unification-one-brain`)
- **⚠️ 코퍼스 위치 교정:** 옛 전제 "work vault = `brain-goodsoo-source`"는 **틀림** — 그 폴더는 `transcripts/`(음성 원자료) 하나뿐. 진짜 코퍼스 = `~/brain-work`+`~/brain-personal`(로컬 홈, **iCloud 아님**). work가 여는 건 통합 `~/brain/`.

## Premises

1. 브레인의 원본은 md 파일이고, work는 그 md를 직접 읽고 편집하는 프론트엔드가 된다. (동의)
2. 데이터는 종류가 셋: **문서**(prose 지식, 내가 씀, work 편집, gbrain 색인) / **레코드**(todo·일정 등 조작 상태, tower 특화) / **색인·청크**(임베딩, gbrain 자동 생성, 안 봄·지워도 재생성). (동의)
3. "한 곳"의 뜻 = 저장소(store)로서의 vault는 전부 md 하나, 지식엔진(engine)으로서의 gbrain은 문서 부분집합만 색인. 캡틴 북극성과 일치. (동의)
4. 소유는 잠금이 아니라 "자연스러운 편집 홈". **읽기는 어디서나 전부 열림(숨김 0), 쓰기만 특화.** work도 레코드를 보여주고 드물게 편집 가능. (캡틴이 벽을 허물어 확정 — 안 보이는 지식 0 원칙)
5. 무결성을 지키는 유일한 불변식 = 앱 소유권이 아니라 **원자적 쓰기 규율(tmp→rename + mtime 충돌 감지)**. 어느 writer든 이걸 지킨다. (동의)
6. work는 **gbrain-work의 업무·프로젝트 문서 편집기가 1차.** 창작·일기(gbrain-personal)는 growth, 회사 문서(angel_brain)는 민감·분리라 후순위/별도. (동의)

## Approaches Considered

- **work 통째로 tower에 흡수(폐기).** Rejected: work의 정교한 Tauri 에디터를 tower의 바닐라·노빌드 스택이 못 담음(재구현 손실 or tower 북극성 위반). 집중된 글쓰기 표면도 잃음.
- **느슨한 결합(work vault를 브레인이 인입).** Rejected: work vault와 브레인 source가 사실상 같은 파일인데 "두 소유자"라 캡틴이 없애려던 흐릿함이 데이터층에 남음.
- **읽기 위주 + 스크래치 승격.** Rejected: 캡틴이 원한 "쉽게 편집"과 반대로 마찰↑, 단일 진실이 다시 둘로 쪼개짐.

## Recommended Approach

**work = 브레인 워크벤치. 하나의 md vault, 렌즈가 다른 앱들.**

각 앱의 축:
- **money** = 돈 (논외, 겹침 0)
- **growth** = 나를 키운다 (게임화 습관 + 창작 글쓰기 + 일기)
- **work → 짱수메모리(`goodsoob-memory`)** = 문서(회의록·글·STT·문서) 읽기·편집, 음성 첨부, AI 요약. 브레인 source md 직접 편집. (이름 근거: 세컨드브레인 감성 유지 + gbrain 엔진과 "누가 진짜 브레인이냐" 충돌 회피)
- **tower** = 관제탑 + 지식엔진 (레코드=todo·일정 특화, 캘린더로 브레인 문서 메타 투영, gbrain 검색·자동화, 포트폴리오 흡수)

운영 규칙:
- **한 폴더(brain vault) = 단일 진실.** work의 vault root = 브레인 source 폴더.
- **읽기 유니버설, 쓰기 특화.** 어느 앱이든 vault 전체를 읽을 수 있음(숨긴 지식 0). 각 앱은 파일시스템에서 **직접** 읽는다(공유 read 코드 없음). 앱은 "무엇을 편집 전문으로 하냐"만 다름 — 문서 홈=work, 레코드 홈=tower. 벽 아님.
  - **scope-creep 가드:** "읽기 유니버설"의 하한 = **raw md 열람**. 리치 렌더(transcript 화자색·AI 요약 UI 등)는 **홈 앱 전용**이다. 안 그러면 tower가 work 에디터를 재구현하게 돼(폐기한 접근의 뒷문) 컨셉 원칙이 scope-creep 엔진이 된다.
  - **레코드 쓰기의 스키마 진실 = tower.** work가 레코드를 편집할 땐 tower의 `plans/*.md` 포맷을 따르는 best-effort. 포맷 정본은 tower가 소유.
- **불변식 = 원자적 쓰기 규율. 단, 지금은 미완성 의존.** work엔 이미 있음(per-path mutex, atomic write). 그러나 **충돌 해소 UX(보존/덮어쓰기 모달)는 CLAUDE.md 상 아직 Phase 6 polish 미완성** — 다중 writer + 실시간 재인입 세계에선 이게 선행 필수다(아래 Next Steps). tower/growth writer에도 같은 원자적 쓰기 규율을 **이식**해야 함(바닐라 Node라 공짜 아님).
- **자동 재인입 파이프라인.** work에서 문서 생성/편집/삭제 → gbrain ingest watcher가 감지 → 자동 재임베딩. 편집이 곧 실시간 지식 갱신.

파편 이사:
- 회의록·내 글·문서 → 브레인 source (work가 편집)
- todo·일정 → tower (레코드, tower가 이미 md로 다룸)
- 루틴/습관 → growth (안 쓰는 work 루틴은 은퇴, 게임화는 growth가 이미 강함)
- 일기 → growth (창작·감성)
- 포트폴리오 → **sync 엔진은 tower**(gh 자동화·크로스프로젝트 = tower 정체성), **카드 본문(글)은 vault 문서**(work 편집·gbrain 색인), **보기는 tower**. 단 우선순위 낮음 — 코어 리팩터 뒤 이관, 그때까진 **work에 잔류(유일한 과도기 예외)**

## Open Questions

1. **vault root 물리 구조 + 레코드 색인 제외 (해결됨).** 결정: work의 vault root = 통합 `~/brain/`, **RESOLVER 택소노미 그대로 편집**(work 앱폴더 강요 X, brain-goodsoo-source 아님). 문서 타입 매핑: 회의록→`meetings/`(신규, RESOLVER에 규칙 추가) / 음성전사→`transcripts/`(brain-goodsoo-source에서 이동) / 글→`creative/` 또는 `notes/` / 일기→`journal/` / Claude세션→`sessions/`(주로 read). **레코드(todo·일정)는 애초에 brain 트리에 없음** — tower가 자기 `plans/*.md`에 보관, 물리적으로 다른 폴더라 gbrain이 자연히 색인 안 함(별도 exclude 규칙 불필요). 통합 실행 시 동명 폴더(concepts/·me/·people/·projects/) 병합 충돌만 스캔.
2. **포트폴리오 편입 세부(행선지는 결정됨).** 결정: sync 엔진→tower, 카드 본문→vault 문서, 보기→tower, 당분간 work 잔류. 남은 미결 = 카드 본문(프로즈)과 구조화 필드(github_pr_id·스크린샷·프로젝트 그룹)를 파일에서 어떻게 나눌지, tower 웹이 Tauri assetProtocol 스크린샷을 어떻게 대체 서빙할지. 커리어 평가자료 성격 유지 필요.
3. **work 새 이름 (결정됨).** 한글 **짱수메모리** / repo **`goodsoob-memory`**. 브랜드명 변경은 저렴, repo slug 리네임은 포트폴리오 sync·경로 영향 있어 선택적·후순위(먼저 브랜드명만).
4. **회사 angel_brain 편집.** 개인 브레인 편집기 안정화 후, 회사 문서(민감·research 맥)를 work로 다룰지 여부 별도 판단.
5. **재인입 debounce (iCloud 리스크는 대폭 축소됨).** work는 undo 스택+1초 commit로 disk write가 잦다 → watcher가 매 저장마다 재임베딩하면 폭주. 저장 시점만/배치/debounce 창 정책 필요. **단, 폴더 모델 교정(Q1)으로 코퍼스가 로컬 `~/brain/`(iCloud 아님)이 되면서 iCloud footgun(`.icloud`·conflicted copy·mtime churn)은 원천 소멸** — 이 설계의 최대 미지수였던 조각이 사라짐. `isSyncNoiseFile` 정합은 안전망으로만.

## Success Criteria

- work를 여는 유일한 이유가 "문서를 읽고 쓴다"로 한 문장에 답 가능.
- work에서 문서 저장 → gbrain 검색 결과에 자동 반영(수동 ingest 0).
- todo·일정을 work에서 찾지 않게 됨(tower에 정착). 일기 위치(통합 brain `journal/` vs growth 게임화)는 미결·deferred. 포트폴리오는 Open Q2 해소 조건부.
- 같은 파일을 두 앱이 만져도 데이터 손실 0(원자적 쓰기 규율 + 충돌 해소 UX 검증됨).

## Distribution Plan

기존 배포 파이프라인이 커버. work=Tauri 데스크탑(`tauri:build`), tower/growth=launchd 상시 실행 로컬 서버. 새 인프라 불필요.

## What I noticed about how you think

- 캡틴은 내 첫 추천(work = "오늘 나의 하루")을 그냥 받지 않고 "캘린더·일정은 전체 그림이라 tower가 맞다"고 근거로 뒤집었다. 실사용 감각이 내 모델보다 정확했고, 그 반박이 전체 설계를 바꿨다.
- "브레인에 원본 문서들은 결국 md 파일이란 말이야?" — 이 한 문장이 work를 "관리앱 잔재"에서 "브레인의 손"으로 리프레임했다. 캡틴은 기능 목록이 아니라 데이터 본질에서 정체성을 찾았다.
- "나의 눈에 안 보이는 지식들이 있다는 건 컨셉에 어긋난다" — 캡틴은 편의가 아니라 컨셉 정합성으로 판단했고, 그 원칙이 "읽기 유니버설·쓰기 특화"라는 더 깔끔한 규칙을 끌어냈다. 내가 세운 "한 필드 한 writer" 벽을 허문 것도 캡틴이다.

## NOT in scope (지금)

- repo slug 리네임(`goodsoob-memory`) — 포트폴리오 sync 경로 영향. 브랜드명만 먼저.
- 회사 angel_brain 편집 — 지금은 hard wall(차단)만. 편집 지원은 별도 판단.

## What already exists (재사용)

- gbrain: md source 폴더 ingest·watcher 이미 있음 — 슬라이스 A ≈ "watcher를 work vault에 겨눔 + 노이즈/ debounce 정합".
